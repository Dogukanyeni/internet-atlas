# Phase 6 — Domain Model and Data Contracts

**Status:** Locked · **Version:** 1.0 · **Date:** 2026-09-01
**Depends on:** [03-information-architecture.md](03-information-architecture.md), [04-architecture.md](04-architecture.md)

Phase 3 wrote the words. Phase 6 turns them into typed contracts that the database, the
API and the frontend all obey. Nothing here touches a database yet — that is Phase 7.

The reason this phase exists before any table: the frontend and backend will be built in
parallel. If the shapes are not fixed first, the frontend invents types, the backend
returns something slightly different, and nobody notices until a user does.

## 2. Identifiers — Q10 answered

**Decision: UUID version 7.**

A UUIDv7 begins with a 48-bit millisecond timestamp, so ids sort by creation time. That
matters in three concrete places:

1. **Index health.** Random UUIDv4 primary keys scatter writes across the whole B-tree.
   Time-ordered ids append instead, which keeps the index compact as the catalog grows
   to tens of thousands of rows.
2. **Cursor pagination.** Ordering by id gives a stable, meaningful order for free, so
   the cursor is just "the last id you saw".
3. **Debugging.** An id tells you roughly when the row was created.

Rejected: **UUIDv4** (bad index locality), **auto-increment integers** (they leak how
many rows exist, and merging data sets becomes painful), **ULID** (same benefits, but it
is stored as text or a custom type instead of the native PostgreSQL `uuid`).

Ids are generated **in the application**, not by the database, so a service can build a
whole object graph in memory before writing anything.

## 3. Audit fields and the public / admin split

Every editorial row carries: `created_at`, `updated_at`, `created_by`, `updated_by`,
`version`.

**Public responses expose only `created_at` and `updated_at`.**

Who wrote a record is editorial metadata. Publishing it is a privacy decision we have
not made, and once it is in a public response it is very hard to take back. Admin
responses carry the full set.

`version` supports optimistic locking: an update sends the version it read, and the API
rejects the write with `version_conflict` if the row changed meanwhile. Without it, two
editors working on the same website silently overwrite each other — a failure that is
almost impossible to notice in a catalog.

## 4. The error contract

```json
{
  "error": {
    "code": "duplicate_domain",
    "message": "A website with this domain already exists.",
    "details": { "domain": "vercel.com" },
    "request_id": "3f8a1c..."
  }
}
```

Three rules:

- **`code` is for machines, `message` is for people.** The frontend switches on `code`
  and never parses `message`, so we can improve the wording — or translate it — without
  breaking a client.
- **`request_id` is always present.** A user sends a screenshot, and that id finds the
  exact request in the logs. Support is impossible without it.
- **Internal details never leak.** An unexpected exception returns a generic message and
  the real reason goes only to the logs.

FastAPI's own validation errors are reshaped into this same envelope, so a client never
has to handle two error formats.

### The code dictionary

| Group | Codes |
|---|---|
| Generic | `validation_error`, `not_found`, `conflict`, `unauthenticated`, `permission_denied`, `rate_limited`, `internal_error`, `service_unavailable` |
| Request shape | `invalid_cursor`, `invalid_sort`, `invalid_filter` |
| Catalog | `slug_taken`, `duplicate_domain`, `invalid_url`, `entity_archived`, `publish_requirements_not_met` |
| Graph | `invalid_relation_pair`, `duplicate_relation`, `self_relation`, `cycle_detected`, `depth_limit_exceeded` |
| Editing | `version_conflict` |

A code is never renamed after release. New ones may appear at any time, so clients must
fall back to `message` for a code they do not know.

## 5. Pagination, sorting, filtering

### Two pagination styles, chosen on purpose

| Style | Shape | Use for |
|---|---|---|
| **Offset** | `?page=2&page_size=50` → `items, total, page, page_size, pages` | Admin tables, where a human wants page numbers and a total |
| **Cursor** | `?cursor=...&limit=50` → `items, next_cursor, has_more` | Everything public that can grow: search, topic lists, graph neighbours |

**Rule:** if a collection can grow without limit, it uses a cursor.

Offset paging gets slower as the offset grows, and — worse — it skips or repeats rows
when data changes while a user is reading. A cursor has neither problem. Cursor
responses deliberately have **no `total`**: counting a large filtered set on every
request is expensive, and a user scrolling an endless list does not need it. Endpoints
that genuinely need counts get a separate facet endpoint in Phase 18.

The cursor is an opaque base64 string. Clients never build or parse one.

### Sorting

`?sort=-created_at` — a leading minus means descending.

Every endpoint declares which fields it allows. Anything else is **rejected**, not
ignored, because a silently ignored sort looks like a broken feature to the user.

### Filtering conventions

| Pattern | Example |
|---|---|
| Single value | `?status=published` |
| Many values, OR | `?category=databases,cloud` |
| By slug, not id | `?topic=vector-databases` |
| Boolean | `?has_relations=true` |

Filters use **slugs, not ids**, so a filtered URL stays readable and shareable — which
decision F-04 (every state is deep-linkable) requires. Each endpoint implements its own
filters in its phase; the conventions are fixed here so they do not drift.

## 6. Response shape naming

| Suffix | Meaning |
|---|---|
| `...Summary` | What a card or list row needs. Small on purpose. |
| `...Detail` | What one full page needs. |
| `...Create` / `...Update` | Admin input. |

**A list endpoint returns summaries, never details.** This is not only about speed: a
list of full records tempts the frontend to render a whole page from a list item, and
then the two shapes slowly drift apart.

`WebsiteDetail` carries its relations inline, because the detail page must answer four
questions on one screen (Phase 2, flow F1): what is it, which area, what is it connected
to, what are the alternatives.

### What input models deliberately do not accept

`WebsiteCreate` has no `id`, no `status` and no `quality_score`. The server owns those.
Letting a client choose an id or publish directly would move editorial rules out of the
service layer, which is exactly where Phase 4 put them.

`RelationCreate` requires `provenance` and `confidence` with **no default**. A default
would let an unsourced fact enter the graph quietly, and data-quality target D2 says
every published relation must say where it came from.

### Nullable versus required

| Rule | Reason |
|---|---|
| Required if the product cannot work without it | `short_description`, `canonical_url`, `kind` |
| Nullable if the real world may not have it | `launch_date`, `logo_url`, `organization_name` |
| Nullable if a later phase fills it | `quality_score` (Phase 25), `last_verified_at` (Phase 26) |
| Never nullable: lists | An empty list is `[]`, never `null`. One less branch in every client. |

`extra="forbid"` is set on every model: an unknown field is a loud error, not a silent
no-op. A typo in a client is found immediately.

## 7. The relation dictionary, now enforceable

`domain/relations.py` holds one rule per relation type: direction, allowed node pairs,
label, inverse label, description. A relation type with no rule cannot exist — there is
a test for that.

Two functions carry the important logic:

- `is_pair_allowed()` — rejects nonsense like "topic built_with technology". For
  undirected types it checks both orders.
- `normalise_pair()` — the single place decision I-05 is applied: an undirected relation
  is stored with the smaller id as source. Without it, "A is an alternative to B" and "B
  is an alternative to A" become two rows, the map draws the edge twice, and the unique
  index cannot help.

There is a test proving that when ids are swapped, their **node types swap with them**.
Getting that wrong would silently corrupt edges.

### `GET /api/v1/meta/enums`

The vocabulary is served to clients instead of being copied into the frontend. Relation
types, their direction and their labels are product rules; if the frontend keeps its own
copy, the two drift and the interface starts showing wrong labels on edges.

## 8. How the contract reaches the frontend

ADR-011 says Pydantic models are the only source of truth. But the endpoints that serve
`WebsiteDetail` and `GraphNeighborhood` do not exist until Phases 9–11.

So `export_openapi.py` also publishes the **domain contract models** into
`components.schemas`, even with no endpoint behind them yet. Without this, the frontend
could not generate types for months and would write them by hand in the meantime —
exactly the drift ADR-011 exists to prevent. These are real Pydantic classes, so what is
published now is what the endpoints will return later.

CI still fails if the committed schema differs from the code.

## 9. Decisions locked in Phase 6

| ID | Decision |
|---|---|
| C-01 | Ids are **UUIDv7**, generated in the application (answers Q10) |
| C-02 | Public responses never expose `created_by`, `updated_by` or `version` |
| C-03 | Updates use optimistic locking through `version` |
| C-04 | One error envelope, with a machine `code` and the `request_id` |
| C-05 | Cursor pagination for anything that can grow; offset only for admin tables |
| C-06 | An unknown sort field is rejected, never ignored |
| C-07 | Filters use slugs, not ids, so URLs stay shareable |
| C-08 | Lists are `[]`, never `null`; unknown input fields are rejected |
| C-09 | Relation validity lives in `domain/relations.py`, and is served at `/meta/enums` |
| C-10 | Domain models are published in the OpenAPI schema before their endpoints exist |
